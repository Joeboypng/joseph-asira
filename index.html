Supermarket Management System (JOE-MART)

Overview

A full-featured supermarket management system built with PHP and MySQL, designed to run in a local XAMPP environment. It replaces manual stock and sales tracking with a structured system covering point-of-sale, inventory, purchasing, staff management, and reporting.

Core Features

  • Point of Sale: product search, cart management, support for cash, mobile money, and card payments, with automatic stock deduction after each sale.
  • Inventory Management: add/edit products, track stock levels, expiry dates, and reorder thresholds.
  • Purchase Orders: create and track supplier orders, with automatic stock updates on delivery.
  • Staff Management: role-based accounts (Manager, Supervisor, Cashier, Stock Clerk) with PIN-based authentication.
  • Reporting: revenue charts, top-selling products, category breakdowns, and cashier performance tracking.

Role-Based Access Control

The system enforces different permission levels per role — for example, only Managers can access Staff Management and only Managers/Supervisors can view Reports or create Purchase Orders, while Cashiers are limited to POS and viewing inventory. This ensures each staff member only has access to what their role requires, following the principle of least privilege.

Tech Stack

PHP, MySQL, PDO (prepared statements for database queries), running on Apache via XAMPP.

e-Voting System

Authentication

In this project, students authenticate by entering their student ID and student email. After both fields are entered, they click “Request OTP” to receive a one-time password sent to their student email. They must enter that OTP correctly before they can access the voting dashboard. This two-step process confirms both identity (ID + email) and live possession of the account (OTP), helping reduce unauthorized access.

Double-Vote Prevention

Each student ID and email is uniquely assigned by the school, so I used them as the base identifier for the voting record. Since friends could know each other’s ID and email and attempt to log in as someone else, I added the OTP step specifically to verify that the person logging in is the actual account owner and not just someone with the right details.

Password Storage

Voters do not use a password at all — they only use their ID, email, and OTP. The admin page is protected by a single password known only to me, and that password is stored as a hash rather than plaintext. This was included because students could try to manipulate the URL to reach the admin area, so the hashed password acts as a final layer of defense if someone finds their way there.

Input Validation

All database queries in this system use prepared statements with parameterized inputs (via PDO), rather than directly inserting user input into SQL strings. This protects against SQL injection across the login and voting flows. Passwords for the admin account are also never compared in plaintext — they're checked using password_verify() against a securely hashed value. User input is additionally sanitized before processing to guard against other common input-based attacks.

Known Limitations

IP-based vote blocking: after a student votes, their IP is blocked from voting again. Limitation: students sharing a network, such as the same campus Wi-Fi or NAT, could share a public IP, which could incorrectly block a legitimate second voter. A VPN could also be used to bypass this control.

OTP brute-force lockout: an account is locked after 4 incorrect OTP attempts to prevent guessing attacks. Anyone blocked for either reason sees an on-screen message to contact me for review. On contact, I manually check whether that student already voted. If they have already voted, the block stays and is treated as an attempted manipulation. If they have not voted, I unblock them and issue a warning.

Building Trust Without Passwords: OTP-Based Voter Verification

In my e-voting project, I wanted a verification method that was secure but still simple for students to use. Instead of creating another password, I used their student ID, student email, and a one-time code to confirm that the person voting was really the account owner.

When I designed the authentication system for my e-voting project, the first challenge was clear: students shouldn't need to create and remember another password just to vote. But I still needed to be certain that the person voting was actually who they claimed to be.

My solution was to use two things every student already has and that are uniquely tied to them by the school: their student ID and their student email. On their own, though, these details aren't enough — friends often know each other's ID numbers or even their email addresses, which means someone could log in pretending to be someone else.

That's where the OTP (one-time password) comes in. After entering their ID and email, students have to click "Request OTP," which sends a one-time code to their student email. Only after entering that correct code do they reach the voting dashboard. This step matters because it proves the person isn't just someone who knows another student's details — they have to actually have live access to that student's email account at that moment.

I think of it as two layers doing two different jobs: the ID and email identify who you're claiming to be, and the OTP verifies you actually are that person. Neither one alone would be enough, but together they cover for each other's weaknesses.

This project also taught me that "no password" doesn't mean "no security" — sometimes removing a password and replacing it with a smarter verification step is actually the safer design, especially for a one-time-use system like voting where account recovery and long-term credential storage aren't the point.

Why the Terminal Isn't Scary: Getting Comfortable with Linux

When I started learning cybersecurity, the command line felt intimidating, but I quickly realized that Linux was less about memorizing random commands and more about learning how systems actually work. The terminal became the place where I could see exactly what was happening and gain confidence in real tools.

When I started learning cybersecurity, most tools and labs assumed I already knew Linux. I didn't, and the command line felt intimidating at first — no icons, no menus, just a blinking cursor waiting for you to type the right thing.

What changed my mind was realizing the CLI isn't an alternative to a GUI, it's more precise than one. A GUI hides what's actually happening; the terminal shows you exactly what command ran and what it did. That matters in security, where you often need to know precisely what a system did, not just that "it worked."

A few things that stood out as I got more comfortable:

  • Permissions matter more than I expected. Commands like chmod and chown aren't just Linux trivia — they're the difference between a secure server and one anyone can tamper with.
  • Everything is scriptable. Once you can chain commands together, repetitive tasks (like log searching with grep or automating scans) go from tedious to fast.
  • Most security tools live here first. Nmap, Wireshark's CLI mode (tshark), Burp Suite's automation, and even basic log analysis all rely on the terminal as a common language.

I'm still early in this, learning basic navigation, permissions, and package management, but the CLI has gone from "the scary black screen" to the tool I reach for first when something needs to be done precisely.
